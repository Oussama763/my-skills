# report-writer

This skill converts messy research notes, ad-hoc analysis, images, and code
into a well-structured LaTeX report and a compiled PDF. Prioritize clarity,
logical sectioning, reproducibility (where code/data exist), and professional
typesetting (captions, labels, references). When invoked, ask clarifying
questions only if the user's intent or required inputs are ambiguous.

## When to trigger

- Trigger when the user mentions any of: "write a report", "generate PDF",
	"produce LaTeX", "compile report", "turn my notes into a report",
	"publishable report", or when they provide a folder of mixed files
	(images/data/code/notes) and ask for a single cohesive document.
- Trigger for tasks that require assembling figures, tables, code listings,
	or a narrative (executive summary, methods, results, recommendations).

## Expected input formats

- Plain text notes (Markdown, txt)
- Data tables: CSV, TSV, JSON
- Images: PNG, JPG, SVG, PDF figures
- Code: .py, .R, .ipynb (notebooks should be exported to script or HTML first)
- Optional: bibliography file (BibTeX .bib)

If files are missing, request them or accept pasted content inline.

## Localization and language options

- Support English and French output. By default produce reports in English
	unless the user explicitly requests French. When French is requested, use
	appropriate LaTeX language packages (`babel` with `french` or `polyglossia`
	and `xelatex` for better font handling) and French typographic conventions
	(e.g., non-breaking spaces before `:`, `;`, `?`, `!`).
- If the user provides content in one language but requests the output in the
	other, ask whether they want an automatic translation (note machine
	translation may need manual edits) or prefer that you keep the original
	language and mark untranslated segments.
- Add a `language` YAML field to the generated `report.tex` frontmatter
	indicating `english` or `french`.

## Output format

- Primary outputs (always): `report.tex` (LaTeX source) and `report.pdf` (compiled)
- Also provide: a `build.sh` or `Makefile` showing how the PDF was produced,
	and a `README.md` with notes on inputs and reproducibility steps.

## Report structure (enforced template)

Always produce LaTeX that follows this template unless the user requests a
different structure:

- Title page: title, authors, affiliations, date
- Abstract / Executive Summary (concise) — 3–6 sentences
- Table of Contents (auto-generated by LaTeX)
- Introduction (motivation, scope)
- Methods / Data (describe data sources and preprocessing; include code
	references as needed)
- Results (figures and tables with captions and labels)
- Discussion (interpretation and limitations)
- Recommendations / Conclusions
- Appendix (extended tables, full code listings, raw outputs)
- References (BibTeX if provided, otherwise numbered list)

Section-level guidance:
- For every figure: include a caption and a one-line interpretation in the
	main text (what this figure shows and why it matters).
- For every table: provide a descriptive caption and units. If the table is
	large, put it in the appendix and include a summary in the Results.
- For code blocks: format as a verbatim or minted listing; mention the
	language and required runtime (e.g., Python 3.10). When a script generated a
	figure, annotate the figure caption with the script name.

## Behavior and heuristics

- Ask at most 2 clarifying questions if essential metadata are missing
	(title/author or which files to include). Otherwise, assume defaults and
	produce a draft the user can revise.
- When given raw data, run lightweight summarization: compute basic
	descriptive stats and include a small summary table or bullet list in
	Methods/Results.
- When multiple images are provided, group logically (e.g., by experiment or
	date) and arrange as subfigures where appropriate.
- Prefer reproducibility: include the exact command used to compile the PDF
	and any scripts used to generate figures or tables in `scripts/`.

## Safety and privacy

- Do not include confidential identifiers unless the user explicitly
	instructs to keep them (ask before including PII). Warn if outputs may
	expose sensitive data in shared PDFs.

## Bundled files and conventions

- `templates/latex-base.tex`: base LaTeX template with placeholders
- `templates/report-class.sty`: lightweight style adjustments (fonts, spacing)
- `scripts/generate_table.py`: helper to convert CSV/JSON -> LaTeX table
- `scripts/compile.sh`: `latexmk -pdf report.tex` or `pdflatex` fallback

Provide these as recommendations; create minimal helper scripts only when
requested or when running the tests.

2. "Turn these research notes and analysis scripts into a reproducible
	 LaTeX report. Include code listings for `analysis.py` and put full
	 datasets in the appendix. Compile to PDF and give me the build command."

3. "Create a short (1–2 page) policy brief from these bullet notes. Add a
	title page and a one-paragraph executive summary, with two supporting
	charts I uploaded. Make the PDF ready for printing. Please produce this
	report in French." 

Ask the user to approve or adjust these test prompts before running automated
or manual tests.

## How to run (recommended workflow)

1. Gather inputs into a directory: `inputs/` (notes, data, images, code).
2. Run helper script (optional):

```bash
python3 scripts/prepare_inputs.py inputs/ workspace/
# produces workspace/report.tex, workspace/scripts/, workspace/assets/
```

3. Compile (from workspace):

```bash
./scripts/compile.sh workspace/report.tex
```

4. Inspect `workspace/report.pdf`. If changes are needed, iterate with the
	 user (edit sections, captions, or reorder figures) and recompile.

## Grading and assertions (for automated evals)

When drafting assertions, prefer objective checks:
- `report.pdf` exists and is non-empty
- All images referenced in `report.tex` exist in `assets/`
- The PDF contains the title string provided in the prompt
- Tables contain at least N rows when derived from CSV inputs

Leave subjective evaluation (writing quality, tone) to human review.

## Iteration and improvements

- After the user reviews the first draft, capture their edits as explicit
	instructions (e.g., "shorten the executive summary", "move Figure 2 to
	Results") and apply them in a new iteration.
- If feedback repeats across cases (e.g., captions are too terse), update
	the template guidance and consider adding a small `scripts/summarize.py`
	helper to create better figure captions automatically.

so the skill triggers reliably for report tasks. When finalized, package the
skill directory as a `.skill` file using the project's packaging script.
